# 백엔드 면접 예상 질문

## JWT 인증

**Q. JWT가 뭔가요? 세션 방식과 어떤 차이가 있나요?**

JWT(JSON Web Token)는 서버가 사용자 정보를 토큰에 직접 담아 클라이언트에 주는 방식입니다.
세션은 서버가 상태를 저장하고 클라이언트는 세션 ID만 가집니다. JWT는 서버가 상태를 저장하지 않아(stateless) 수평 확장이 쉽습니다.
단점은 토큰을 서버에서 강제로 무효화하기 어렵다는 점입니다.

Neatly에서는 `auth.py`에서 `python-jose`로 HS256 알고리즘 JWT를 발급하고, 만료 시간은 24시간입니다.

---

**Q. Neatly에서 JWT를 어떻게 발급하고 검증하나요?**

발급: 로그인 성공 시 `create_access_token({"sub": user_id})`로 사용자 ID를 페이로드에 담아 반환합니다.

검증: 모든 보호된 엔드포인트는 `Depends(get_current_user)`를 사용합니다. 이 함수는 `Authorization: Bearer <token>` 헤더에서 토큰을 꺼내 `jwt.decode()`로 검증하고, payload의 `sub`로 DB에서 사용자를 조회합니다.

---

**Q. bcrypt로 비밀번호를 왜 해시하나요? md5나 sha256은 안 되나요?**

md5, sha256은 빠른 해시라 레인보우 테이블 공격에 취약합니다. bcrypt는 의도적으로 느리게 설계되어 있고, 매번 다른 salt를 자동으로 생성합니다. 같은 비밀번호도 매번 다른 해시가 나와서 레인보우 테이블 공격을 막습니다.

Neatly에서는 `bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt())`로 저장하고, `bcrypt.checkpw()`로 검증합니다.

## FastAPI

**Q. FastAPI의 Depends가 뭔가요?**

의존성 주입(Dependency Injection) 시스템입니다. 여러 엔드포인트에서 공통으로 필요한 로직(DB 세션 생성, 사용자 인증 등)을 함수로 분리하고 `Depends()`로 주입합니다.

Neatly에서는 `Depends(get_db)`로 DB 세션을, `Depends(get_current_user)`로 현재 유저를 자동 주입합니다.

---

**Q. get_db()에서 yield를 쓰는 이유가 뭔가요?**

`yield`를 사용하면 요청 처리 전에 세션을 열고, 요청이 끝난 뒤 `finally` 블록에서 반드시 세션을 닫을 수 있습니다. try/finally 구조로 예외가 발생해도 DB 연결이 누수되지 않습니다.

---

**Q. FastAPI에서 비동기(async)를 왜 쓰나요?**

WebSocket처럼 다수의 연결을 동시에 유지해야 하는 경우 async가 필수입니다. 일반 REST 엔드포인트는 SQLAlchemy가 동기 드라이버를 쓰므로 동기 def로도 충분하며, FastAPI가 스레드풀에서 처리합니다.

## ORM / DB

**Q. N+1 쿼리 문제가 뭔가요? Neatly에서 어떻게 해결했나요?**

N개 문서를 조회한 뒤 각 문서의 태그를 개별 쿼리로 N번 조회하면 총 N+1번 쿼리가 실행됩니다. 문서 100개 = 쿼리 101회.

`docs_with_tags_batch()`로 해결했습니다. 전체 문서 ID 목록을 IN 쿼리 한 번으로 태그를 일괄 조회한 뒤 메모리에서 매핑합니다. 쿼리 수가 N+1 → 2로 감소합니다.

---

**Q. SQLAlchemy에서 db.commit() 후 객체에 접근하면 어떻게 되나요?**

commit() 후 SQLAlchemy는 세션의 모든 인스턴스를 expire 처리합니다. 이후 해당 객체의 속성에 접근하면 자동으로 DB에서 다시 로드(lazy load)합니다. 세션이 닫혀 있으면 `DetachedInstanceError`가 발생합니다.

---

## Google OAuth / Gmail

**Q. OAuth 2.0 흐름을 설명해주세요.**

1. 서버가 Google 인가 URL을 생성해 클라이언트에 반환
2. 사용자가 Google 로그인 및 권한 동의
3. Google이 인가 코드(code)를 콜백 URL로 전달
4. 서버가 코드를 Google에 보내 access_token + refresh_token 교환
5. access_token으로 Gmail API 호출

Neatly에서 `google-auth-oauthlib` 대신 `requests_oauthlib`을 쓴 이유는, 최신 버전이 PKCE를 자동 추가하는데 서버사이드 흐름에서 `code_verifier`를 요청 사이에 유지할 방법이 없어 "Missing code verifier" 오류가 났기 때문입니다.

---

**Q. access_token이 만료되면 어떻게 처리하나요?**

`gmail_utils.py`의 `refresh_if_expired()`에서 처리합니다. `creds.expiry is None`이거나 `creds.expired`가 True이면 refresh_token으로 Google에 새 access_token을 요청하고, 갱신된 토큰과 만료 시각을 DB에 즉시 저장합니다.

초기에 OAuth 콜백에서 `expires_at`을 저장하지 않아 `creds.expired`가 항상 False였고 갱신이 전혀 안 되는 버그가 있었습니다. 연결 후 1시간이 지나면 silent 실패가 발생하는 원인이었습니다.

## WebSocket

**Q. WebSocket과 HTTP의 차이가 뭔가요?**

HTTP는 요청-응답 구조로 클라이언트가 먼저 요청해야 합니다. WebSocket은 최초 핸드셰이크 후 서버-클라이언트 간 양방향 지속 연결이 유지됩니다. 실시간 채팅처럼 서버가 먼저 데이터를 푸시해야 하는 경우에 적합합니다.

---

**Q. ConnectionManager가 뭔가요? 왜 만들었나요?**

채팅방별 WebSocket 연결 목록을 관리하는 클래스입니다. `rooms` dict에 `{room_id: [(ws, user_id, user_name), ...]}` 구조로 저장합니다.

재연결 시 같은 `user_id`의 기존 연결을 `close()` 후 교체하는 로직이 있어 중복 메시지 수신을 방지합니다. WebSocket 엔드포인트는 `Depends(get_db)`가 동작하지 않아 `SessionLocal()`을 직접 생성합니다.

## 스케줄러

**Q. APScheduler로 어떤 작업을 처리하나요?**

세 가지 백그라운드 작업을 등록했습니다.

1. `IntervalTrigger(minutes=2)` — Premium 사용자 Gmail 자동 동기화
2. `CronTrigger(hour=8)` — 매일 오전 8시 AI 일간 브리핑 자동 생성
3. `CronTrigger(hour=3)` — 매일 새벽 3시 휴지통 30일 경과 문서 영구 삭제

FastAPI 앱 시작 시 `start_scheduler()`를 호출하고, 이미 실행 중이면 중복 등록하지 않습니다.

---

**Q. Render 무료 플랜에서 스케줄러가 제대로 작동하나요?**

Render 무료 플랜은 15분 비활성 시 서버가 sleep 상태로 전환됩니다. sleep 중에는 APScheduler도 멈추므로 자동 동기화와 브리핑 생성이 실행되지 않을 수 있습니다. 이는 알려진 한계이며 개선 방향으로 keep-alive ping 또는 유료 플랜 전환을 고려하고 있습니다.
