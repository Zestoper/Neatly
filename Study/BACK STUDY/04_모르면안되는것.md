## 1. JWT 구조와 보안

JWT는 `header.payload.signature` 세 파트로 구성됩니다.

```
eyJhbGciOiJIUzI1NiJ9   ← header (base64)
.eyJzdWIiOiJ1c2VyMSJ9 ← payload (base64) — 암호화 아님, 누구나 디코딩 가능
.SflKxwRJSMeKKF2QT4fw  ← signature (SECRET_KEY로 서명)
```

- payload는 암호화가 아닌 base64 인코딩입니다. 누구나 디코딩해 볼 수 있습니다.
- 따라서 payload에 비밀번호, 카드번호 등 민감한 정보를 담으면 안 됩니다.
- 무결성은 signature로 보장합니다. SECRET_KEY 없이는 서명을 위조할 수 없습니다.
- **Neatly의 보안 취약점**: JWT를 localStorage에 저장합니다. XSS 공격 시 탈취 가능합니다. 개선 방향은 httpOnly Cookie로 전환입니다.

## 2. bcrypt salt와 단방향 해시

```python
hash1 = bcrypt.hashpw(b"password123", bcrypt.gensalt())
hash2 = bcrypt.hashpw(b"password123", bcrypt.gensalt())
# hash1 != hash2 — 같은 비밀번호도 salt 때문에 다른 해시
```

- `gensalt()`가 매번 다른 랜덤 salt를 생성합니다.
- salt가 해시 안에 포함되어 있어 `checkpw()`가 꺼내서 비교합니다.
- 단방향 해시라 원래 비밀번호를 복원할 수 없습니다.

## 3. HTTP 상태 코드

| 코드 | 의미 | Neatly 사용 예 |
|------|------|---------------|
| 200 | 성공 | 기본 응답 |
| 201 | 생성 성공 | (사용 안 함, 200으로 처리) |
| 400 | 잘못된 요청 | 이메일/비밀번호 오류, Gmail 미연결 |
| 401 | 인증 실패 | JWT 만료/변조 |
| 403 | 권한 없음 | Premium 기능을 일반 플랜이 요청 |
| 404 | 찾을 수 없음 | 문서/사용자 없음 |
| 422 | 유효성 검사 실패 | Pydantic 타입 오류 |
| 502 | 외부 서비스 오류 | Groq API 실패 |

## 4. CORS

브라우저는 다른 도메인(origin)으로의 요청을 기본적으로 차단합니다. 백엔드가 CORS 헤더를 응답에 포함시켜야 합니다.

```python
# main.py
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173", "https://neatly.vercel.app"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

- `allow_origins=["*"]`는 모든 도메인을 허용하므로 프로덕션에서는 쓰면 안 됩니다.
- `allow_credentials=True`이면 `allow_origins`에 `"*"`를 쓸 수 없습니다.

## 5. OAuth 2.0 access_token vs refresh_token

| | access_token | refresh_token |
|---|---|---|
| 수명 | 1시간 | 수개월~영구 |
| 용도 | API 직접 호출 | access_token 재발급 |
| 저장 | DB (평문) | DB (평문) |
| 탈취 시 위험 | 1시간 후 만료 | 무기한 API 접근 가능 |

Neatly의 개선 방향: DB에 암호화 저장 (현재 평문).

## 6. 동기 vs 비동기 라우터

```python
# 동기 — FastAPI가 threadpool에서 실행
@router.get("/documents")
def get_documents():
    ...

# 비동기 — 이벤트 루프에서 실행
@router.websocket("/ws/{room_id}")
async def websocket_endpoint(ws: WebSocket):
    ...
```

- SQLAlchemy는 동기 드라이버를 쓰므로 DB 쿼리가 있는 엔드포인트는 동기 `def`로 작성합니다.
- 비동기 `def` 안에서 동기 SQLAlchemy를 쓰면 이벤트 루프가 블로킹되는 문제가 생깁니다.
- WebSocket처럼 실시간 I/O가 필요한 경우에만 `async def`를 씁니다.

## 7. 데이터베이스 인덱스

```python
class Document(Base):
    __table_args__ = (
        Index("ix_document_user_deleted", "user_id", "deleted_at"),
        Index("ix_document_user_created", "user_id", "created_at"),
    )
    gmail_message_id = Column(String(255), nullable=True, index=True)
```

- 자주 필터링하는 컬럼에 인덱스를 걸어야 쿼리 속도가 빠릅니다.
- `user_id + deleted_at` 복합 인덱스: 특정 유저의 휴지통 아닌 문서를 빠르게 조회합니다.
- `gmail_message_id` 단일 인덱스: 중복 메일 체크 쿼리를 빠르게 합니다.

## 8. Pydantic EmailStr vs 일반 str

```python
class LoginRequest(BaseModel):
    email: EmailStr  # 422 자동 반환
    password: str
```

- `EmailStr`은 `pydantic[email]` 의존성이 필요합니다 (`pip install pydantic[email]`).
- `@` 없거나 형식 오류인 경우 FastAPI가 자동으로 `422 Unprocessable Entity`를 반환합니다.
- 별도의 유효성 검사 코드를 작성할 필요가 없습니다.

## 9. UUID vs 정수 PK

Neatly는 모든 테이블의 PK로 UUID(`String(36)`)를 사용합니다.

```python
id = Column(String(36), primary_key=True, default=lambda: str(uuid.uuid4()))
```

- 정수 PK는 순서가 예측 가능합니다(`/documents/1`, `/documents/2`). URL로 다른 사용자의 리소스를 추측할 수 있습니다.
- UUID는 전역으로 고유하고 추측이 어렵습니다.
- 단점: 문자열이라 정수보다 저장 공간이 크고, 인덱스 성능이 약간 낮습니다.

## 10. silent 실패 패턴의 위험성

```python
try:
    results = service.users().messages().list(...).execute()
except Exception:
    return 0  # Gmail API 실패를 조용히 처리
```

이 패턴은 Gmail API가 401, 403, 네트워크 오류 등 어떤 이유로 실패해도 0을 반환합니다. 호출자는 "새 이메일 없음"과 "API 오류"를 구분할 수 없습니다.

프로덕션에서는 최소한 로그를 남기고, 가능하면 오류 유형을 구분해서 적절한 상태 코드로 반환해야 합니다.
