# Neatly 면접 질문 & 답변

---

## 프로젝트 소개

**Q. Neatly 프로젝트 간단히 소개해주세요.**

이메일과 문서를 한 곳에서 관리하기 어려운 문제를 해결하기 위해 만든 AI 기반 이메일·문서 관리 서비스입니다. Gmail과 연동하여 받은 메일을 AI로 요약해주고, 필요 시 AI로 메일을 작성해서 발송할 수 있습니다. 문서화 기능과 일정 알림 기능도 있습니다.

---

## 기술 스택

**Q. 기술 스택이 어떻게 되나요?**

백엔드는 FastAPI, 프론트엔드는 React를 사용했습니다. DB는 PostgreSQL(Supabase)을 사용했고, 배포는 Vercel과 Render를 사용했습니다. 인증은 JWT, AI는 Groq의 LLaMA 3.3 70B 모델을 사용했습니다.

---

## 인증

**Q. JWT 인증을 어떻게 구현했나요?**

JWT는 header, payload, signature로 구성됩니다. header에는 토큰 타입과 알고리즘인 HS256을 넣었고, payload에는 만료 시간과 유저 id를 넣었습니다. signature에는 시크릿 키를 넣어서 localStorage에 저장했습니다. 보안 취약점으로는 XSS 공격 시 탈취 가능합니다. 개선 방향으로는 httpOnly Cookie로 전환하면 됩니다.

---

**Q. 비밀번호를 어떻게 저장했나요?**

bcrypt로 해싱 처리했습니다. 암호화는 양방향이라 DB가 털리면 원문 복구가 가능하지만, bcrypt는 단방향 해시라 복구가 불가능합니다. salt를 사용해서 같은 비밀번호도 매번 다른 해시값이 나옵니다. 레인보우 테이블 공격을 방어할 수 있습니다.

> **레인보우 테이블**: 해시값 → 원래 비밀번호를 역조회하기 위해 미리 계산해둔 표. salt가 있으면 같은 비밀번호도 해시값이 매번 달라서 표를 만드는 게 불가능해집니다.

## API / 네트워크

**Q. Axios 인터셉터를 왜 썼나요?**

API가 100개 있으면 JWT를 100번 갖다 붙여야 하고, 401 에러가 나면 토큰 삭제하고 로그인 페이지로 이동하는 것도 100번 해야 하는 번거로움이 있습니다. Axios 인터셉터를 사용해서 공통 처리를 한 곳에 모아 1번으로 줄였습니다.

- **요청 인터셉터**: 모든 요청에 JWT를 자동으로 붙임
- **응답 인터셉터**: 401 응답 시 토큰 삭제 후 로그인 페이지로 이동

## Gmail 동기화

**Q. Gmail 동기화가 어떻게 동작하나요?**

Premium 유저 중 Gmail이 연결된 유저만 대상으로 APScheduler를 사용해서 2분마다 자동으로 실행됩니다. 동기화할 때 access_token이 만료됐으면 refresh_token으로 자동 갱신 후 Gmail API를 호출합니다. 중복 저장 방지는 gmail_message_id로 이미 저장된 메일인지 확인 후 새 메일만 저장합니다.

---

**Q. OAuth 2.0 흐름을 설명해주세요.**

1. "Gmail 연결" 버튼 클릭
2. Google 로그인 페이지로 이동
3. 사용자가 권한 허용
4. Google이 code(임시 티켓) 전송
5. 백엔드가 code를 access_token, refresh_token으로 교환
6. DB에 저장
7. 이메일 동기화할 때 access_token 사용
8. access_token 만료되면 refresh_token으로 자동 갱신

> **access_token vs refresh_token**: access_token은 1시간짜리 입장권, refresh_token은 재발급 쿠폰. access_token이 만료되면 refresh_token으로 새로 발급받습니다.

## 성능 최적화

**Q. N+1 문제가 뭔가요? Neatly에서 어떻게 해결했나요?**

문서가 100개 있으면 태그 조회 쿼리가 100번 나가는 문제입니다. `docs_with_tags_batch()`로 IN 쿼리를 써서 한 번에 전체 태그를 조회해서 100번에서 1번으로 줄였습니다.

---

## 트러블슈팅

**Q. 트러블슈팅 경험이 있나요?**

사용자가 동기화 버튼을 눌렀는데 아무 반응이 없었습니다. 코드를 확인해보니 `handleGmailSync`에 성공 시 토스트 알림과 문서 목록 갱신 코드가 없었습니다. 성공/실패 분기를 추가해서 해결했습니다.

**추가 트러블슈팅:**

- **Gmail 1시간 후 silent 실패**: OAuth 콜백에서 `expires_at`을 DB에 저장하지 않아 토큰 갱신이 안 됐습니다. `expires_at` 저장과 `creds.expiry is None` 조건 추가로 해결했습니다.
- **Render 콜드 스타트**: `timeout: 90000`으로 늘리고 `warmUpServer()`로 미리 깨우는 방식으로 해결했습니다.

## React

**Q. Context API가 뭔가요? Neatly에서 어떻게 썼나요?**

컴포넌트에 props를 일일이 내려주지 않고 전역으로 값을 공유하는 방법입니다. Neatly에서는 `App.tsx`에 `ToastContext`로 전체 앱을 감싸서 어떤 페이지에서든 `useToast()`로 `showToast`를 바로 호출할 수 있게 했습니다.

---

**Q. SPA에서 새로고침하면 404가 나는 이유가 뭔가요? 어떻게 해결했나요?**

모든 페이지는 `index.html` 하나로 관리하는데, `/documents`로 직접 접속하면 서버가 `documents` 파일을 찾습니다. 그런 파일이 없으니 404가 납니다. `vercel.json`에 모든 경로를 `index.html`로 rewrite 설정을 추가해서 React가 URL을 읽어 맞는 페이지를 렌더링하게 했습니다.

---

## 데이터베이스

**Q. 데이터베이스 설계에서 신경 쓴 부분이 있나요?**

두 가지를 신경 썼습니다. 첫째, 정수 PK 대신 UUID를 사용했습니다. 정수 PK는 `/documents/1`, `/documents/2`처럼 순서가 예측 가능해서 다른 유저 리소스를 URL로 추측할 수 있습니다. UUID는 추측이 불가능해서 보안상 안전합니다. 둘째, 자주 조회하는 `user_id + deleted_at`에 복합 인덱스를 걸어서 쿼리 속도를 높였습니다.

## 플랜 제한

**Q. 프리미엄 플랜 기능은 어떻게 제한했나요?**

백엔드에서 API 호출 시 유저의 플랜을 확인해서 PREMIUM이 아니면 403을 반환했습니다. 프론트엔드에서도 플랜에 따라 버튼을 숨기거나 비활성화 처리했습니다.

> **403**: 권한 없음. 401(인증 실패 — 로그인 안 됨)과 다릅니다. 403은 로그인은 됐지만 권한이 없는 경우입니다.

## 실시간

**Q. WebSocket을 왜 썼나요?**

HTTP로 구현하면 새 메시지가 왔는지 클라이언트가 계속 서버에 물어봐야 합니다. 불필요한 요청이 많아지고 실시간성이 떨어집니다. WebSocket은 연결이 유지되어 서버가 메시지를 바로 푸시해줄 수 있어서 효율적입니다.
