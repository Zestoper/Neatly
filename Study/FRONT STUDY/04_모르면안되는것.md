# 프론트엔드 모르면 안 되는 것

---

## 1. SPA vs MPA

| | SPA | MPA |
|---|---|---|
| 초기 로딩 | 느림 (JS 번들 전체) | 빠름 |
| 페이지 이동 | 빠름 (JS로 처리) | 느림 (서버 왕복) |
| SEO | 약함 (SSR 없으면) | 강함 |
| 예시 | Neatly (Vite + React) | 전통적 서버 렌더링 |

Neatly는 SPA입니다. `index.html` 하나에 React가 모든 라우팅을 처리합니다. Vercel에 `vercel.json`으로 모든 경로를 `index.html`로 rewrite하는 이유가 이것입니다.

```json
// vercel.json
{ "rewrites": [{ "source": "/(.*)", "destination": "/" }] }
```

## 2. JWT를 localStorage에 저장하는 것의 위험성

Neatly는 JWT를 `localStorage`에 저장합니다.

```typescript
localStorage.setItem("token", data.token);
const token = localStorage.getItem("token");
```

**위험**: XSS(Cross-Site Scripting) 공격 시 자바스크립트로 `localStorage`에 접근할 수 있으므로 토큰이 탈취됩니다.

**더 안전한 방법**: `httpOnly` Cookie에 저장합니다. 자바스크립트에서 읽을 수 없어 XSS에 안전합니다. 단, CSRF 공격에 대한 별도 방어가 필요합니다.

Neatly에서 현재 XSS가 발생하지 않는 이유: React는 JSX에서 문자열을 자동으로 이스케이프하므로 일반적인 XSS는 방어됩니다. 하지만 구조적 취약점은 남아 있습니다.

## 3. 가상 DOM (Virtual DOM)

React는 실제 DOM을 직접 수정하지 않고 가상 DOM(메모리 상의 DOM 트리)을 먼저 변경한 뒤, 이전 가상 DOM과 비교(diffing)해 실제로 바뀐 부분만 실제 DOM에 반영합니다.

- **이점**: 실제 DOM 조작은 비쌉니다. 가상 DOM 비교 후 최소한의 실제 DOM 변경만 합니다.
- **리렌더링**: 상태/props가 바뀌면 해당 컴포넌트와 하위 컴포넌트 전체를 다시 렌더링합니다. 가상 DOM 비교가 있어도 불필요한 리렌더가 많으면 느려집니다.
- **`key` prop**: 리스트 렌더링 시 어떤 항목이 변경/추가/삭제됐는지 추적합니다. `key`가 없으면 잘못된 항목을 업데이트할 수 있습니다.

## 4. CSS Modules가 전역 CSS보다 나은 이유

```typescript
import styles from "./Dashboard.module.css";
<div className={styles.container}>
```

- 빌드 시 `.container`가 `Dashboard_container__xK3mP`처럼 고유하게 변환됩니다.
- 다른 파일에 같은 이름의 클래스가 있어도 충돌하지 않습니다.
- 전역 CSS에서는 `.container`가 어디서든 적용되어 의도치 않은 스타일 덮어쓰기가 발생합니다.

Neatly에서 각 페이지마다 `.module.css` 파일이 별도로 있는 이유입니다.

## 5. Vite가 CRA(Create React App)보다 빠른 이유

- **개발 서버**: Vite는 네이티브 ES Modules를 그대로 브라우저에 제공합니다. CRA는 전체를 번들링한 뒤 서버를 시작합니다. 파일이 많을수록 차이가 커집니다.
- **HMR**: 파일을 수정하면 해당 모듈만 교체합니다. CRA는 전체 재번들링에 가깝습니다.
- **프로덕션 빌드**: Rollup을 사용합니다.
- **환경 변수**: `VITE_` 접두사가 없으면 클라이언트 코드에 노출되지 않습니다.

```
VITE_API_BASE_URL=http://localhost:8000  # 노출됨
SECRET_KEY=abc123                        # 노출 안 됨
```

## 6. CORS — 프론트엔드 관점

CORS 에러는 **브라우저**가 막는 것입니다. 서버는 응답을 보내지만 브라우저가 스크립트에서 읽지 못하게 합니다.

- Postman이나 curl에서는 CORS 에러가 없습니다. 브라우저만 적용합니다.
- 백엔드가 `Access-Control-Allow-Origin` 헤더를 응답에 포함시켜야 브라우저가 허용합니다.
- Neatly 프론트는 Vercel(`https://neatly.vercel.app`)에서 Render(`https://neatly-backend.onrender.com`)로 요청을 보냅니다. 백엔드 `main.py`에 허용 origin이 명시돼 있어야 합니다.

프론트엔드 개발자가 CORS 에러를 만났을 때 직접 할 수 있는 것: Vite `proxy` 설정으로 개발 중 우회합니다. 프로덕션에서는 백엔드 설정을 바꿔야 합니다.

## 7. 브라우저 스토리지 비교

| | localStorage | sessionStorage | Cookie |
|---|---|---|---|
| 수명 | 직접 삭제 전까지 | 탭 닫으면 삭제 | 만료일 설정 가능 |
| 용량 | ~5MB | ~5MB | ~4KB |
| 서버 전송 | 안 됨 | 안 됨 | 자동 전송 |
| JS 접근 | 가능 | 가능 | httpOnly이면 불가 |

Neatly의 선택:
- `token` → localStorage (새로고침 후에도 유지)
- `plan`, `userName` → localStorage (UI 렌더링에 필요)
- sessionStorage, Cookie는 사용하지 않음

## 8. Notification API 크로스 플랫폼 차이

```typescript
// Neatly useCalendarNotifications.ts
if (typeof Notification !== "undefined" && Notification.permission === "granted") {
    new Notification(event.title);
} else {
    showCalendarAlert("일정 알림", event.title);  // 인앱 폴백
}
```

| 환경 | Notification API |
|---|---|
| Chrome (Desktop) | 지원 |
| Safari (Mac) | 지원 (15.4+) |
| iOS Safari | 미지원 (`undefined`) |
| 안드로이드 Chrome | 지원 |

iOS Safari에서 `window.Notification`이 `undefined`입니다. `Notification.requestPermission()`을 가드 없이 호출하면 런타임 오류가 발생합니다.

`typeof Notification !== "undefined"` 가드가 없으면 iOS에서 앱 전체가 흰 화면이 됩니다. `ErrorBoundary`가 두 번째 방어선입니다.

## 9. ErrorBoundary가 반드시 클래스 컴포넌트인 이유

React에서 렌더링 중 발생한 오류를 잡는 `getDerivedStateFromError`와 `componentDidCatch`는 클래스 컴포넌트 생명주기 메서드입니다. 함수형 컴포넌트에는 동등한 훅이 없습니다.

```typescript
// 함수형으로는 구현 불가
static getDerivedStateFromError() {
    return { hasError: true };
}
```

`try/catch`는 이벤트 핸들러 안에서만 동작합니다. JSX 렌더링(`return <div>`) 중 발생한 오류는 `try/catch`로 잡을 수 없습니다. ErrorBoundary만 가능합니다.

## 10. Axios의 `redirecting` 플래그 패턴

```typescript
// client.ts
let redirecting = false;

api.interceptors.response.use(
    (response) => response,
    (error) => {
        if (error.response?.status === 401 && !redirecting) {
            redirecting = true;
            localStorage.removeItem("token");
            window.location.href = "/login";
        }
        return Promise.reject(error);
    }
);
```

페이지 하나가 여러 API를 동시에 호출할 때(예: `Promise.all`), 모두 401을 받으면 인터셉터가 여러 번 실행됩니다. `redirecting` 플래그가 없으면 `window.location.href = "/login"`이 여러 번 실행됩니다. 실제로는 큰 문제가 안 되지만 불필요한 리다이렉트와 `localStorage.removeItem` 중복 실행을 방지합니다.

모듈 스코프(`let redirecting`)에 선언되어 있어서 앱 전체에서 하나의 인스턴스를 공유합니다.

## 11. React 렌더링 순서

```
1. 부모 컴포넌트 함수 실행 (JSX 반환)
2. 자식 컴포넌트 함수 실행
3. 가상 DOM 비교 (diffing)
4. 실제 DOM 변경
5. useEffect 실행 (렌더링 완료 후)
```

`useEffect`가 렌더링 후 실행되는 이유: DOM 업데이트가 완료된 뒤 부수 효과(API 호출, 구독)를 실행하기 위해서입니다. 렌더링 도중 실행되면 상태 변경이 또 렌더링을 유발하는 무한 루프가 생길 수 있습니다.

## 12. Render 무료 플랜 콜드 스타트 대응

Render 무료 플랜은 15분 동안 요청이 없으면 서버가 sleep합니다. 다음 요청 시 콜드 스타트로 최대 60초 지연이 발생합니다.

Neatly의 대응:
1. `client.ts`의 `timeout: 90000` (90초) — 콜드 스타트 중 타임아웃 방지
2. `warmUpServer()` — 로그인/회원가입 페이지 진입 시 백엔드에 미리 요청을 보내 sleep 상태를 깨움

```typescript
export async function warmUpServer() {
    try { await api.get("/health"); } catch {}
}
```

이 함수는 실패해도 무시합니다. 사용자 경험 개선 목적이므로 오류를 노출할 필요가 없습니다.
